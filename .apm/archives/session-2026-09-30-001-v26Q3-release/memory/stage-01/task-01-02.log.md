# Task 1.2 - Package Split

## Summary
Split the monolithic `app/bot.py` (1039 lines) into `app/discord_bot/` (`client.py`, `commands.py`, `views.py`, `timer.py`, `lifecycle.py`, `__init__.py`) as a pure move-only refactor, using a mixin composition for `TeaModeBot`. All 122 tests pass with only import/patch-path changes; the full validation pipeline (ruff format, ruff check, pytest, bare pyright, injection scan) is clean.

### Circular-import approach: mixins

Chose the mixin approach named in the Task Prompt: `TimerMixin`, `LifecycleMixin`, `ViewsMixin`, `CommandsMixin` — plain classes with no `__init__` of their own, whose methods reference `self._registry`, `self.client`, `self._edit_states`, etc. `TeaModeBot(CommandsMixin, ViewsMixin, TimerMixin, LifecycleMixin)` in `client.py` defines the real `__init__` that populates every attribute the mixins expect, plus the discord.py wiring (`self.client.event(...)`).

Import direction is one-way: `client.py` imports `commands.py`, `views.py`, `timer.py`, `lifecycle.py`; none of those import `client.py` at runtime. The one place a mixin module needs the `TeaModeBot` type (the `bot: TeaModeBot` parameter on `IntentionModal.__init__` in `views.py`) uses `if TYPE_CHECKING: from app.discord_bot.client import TeaModeBot`, which `from __future__ import annotations` makes purely a static-analysis import — no runtime cycle. `views.py`'s `ViewsMixin._handle_timer_pick` constructs `IntentionModal(bot=cast("TeaModeBot", self), ...)` — a string-literal cast (also erased at runtime, resolved by pyright via the `TYPE_CHECKING` import) since `self` is statically `ViewsMixin`, not `TeaModeBot`, from inside the mixin's own module.

Each mixin class declares the attributes it reads from `self` (`client`, `_registry`, `_edit_states`, etc.) as class-level type annotations with no assignment — e.g. `_registry: SessionRegistry` — purely so pyright can type-check each mixin module in isolation without seeing `TeaModeBot.__init__`. This was necessary: without it, bare `pyright` reported 43 `reportAttributeAccessIssue` errors (`Cannot access attribute "_registry" for class "LifecycleMixin*"` and similar) because pyright analyzes each mixin against its own MRO, not the eventual composed class. Adding the declarations resolved all 43 errors with 0 behavior change (they are declarations only, never assigned in the mixin).

Event handlers kept their `on_<event>` names throughout (`on_ready`, `on_interaction`, `on_raw_reaction_add`, `on_voice_state_update`) since `client.event(self.on_ready)` etc. in `client.py.__init__` routes by the bound method's `__name__`, which is unaffected by which mixin module defines the method.
