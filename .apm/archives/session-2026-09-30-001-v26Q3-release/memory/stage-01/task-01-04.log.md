## Details
1. Enabled `extend-select = ["ANN"]` in `pyproject.toml` for `app/` and
   `teamode.py` (tests/ stays exempt). `ruff check --select ANN` reported
   zero violations — the codebase was already fully annotated (the
   `from __future__ import annotations` + existing signatures already
   satisfied `ANN`), so no annotations needed to be added.
2. Removed and re-verified all 13 `cast()`/`# type: ignore` occurrences
   with pyright after each group (see table below).
3. Two of the thirteen (both in `lifecycle.py`) were already fixed as a
   side effect of Task 1.3's string-literal move, then deliberately
   reverted back to `cast`/`# type: ignore` at the end of that Task once I
   found the existing tests pass plain unspec'd `AsyncMock()` channel
   fakes that fail `isinstance(..., discord.abc.Messageable)` — flagged in
   the Task 1.3 log. This Task re-did that isinstance narrowing properly,
   updating the four affected test fixtures to `AsyncMock(spec=discord.TextChannel)`
   (matching the project's own Test Patterns convention: "Use
   `MagicMock(spec=discord.VoiceChannel)` (etc.) so `isinstance` narrowing
   works").
4. Two `_handle_handoff` narrowings needed a bit more than a bare
   `isinstance`:
   - Guard 1 switched from `interaction.channel.id` to
     `interaction.channel_id` (per the Task Prompt's suggestion) — this
     required updating `_make_handoff_interaction` in
     `tests/test_session_handoff.py` to also set `inter.channel_id`
     (a plain `AsyncMock()` doesn't derive `channel_id` from `channel.id`
     the way real discord.py does), otherwise 5 handoff tests failed
     because the mock `channel_id` attribute auto-vivified as a truthy
     Mock instead of `None`/an int.
   - Guard 2 (target-in-voice-channel) is narrowed with
     `isinstance(voice_channel, discord.VoiceChannel)`; `member` was
     already typed `discord.Member` from the slash-command signature, so
     no separate narrowing was needed there.
5. `IntentionModal`'s `text_input = cast(...)` was replaced with an
   `isinstance(component, discord.ui.TextInput)` guard (logging an error
   and falling back to `""` on the — genuinely impossible — else branch),
   since `discord.ui.Label.component` is typed as the broader `Item` in
   discord.py's stubs.
6. `timer_message = await cast(discord.VoiceChannel, interaction.channel).send(...)`
   and `channel = cast(discord.abc.Messageable | None, interaction.channel)`
   were both replaced by reusing `self._voice_channel` / `voice_channel` —
   the already-narrowed `discord.VoiceChannel` reference the modal was
   constructed with — rather than re-deriving the type from
   `interaction.channel`. This is the "reuse the already-narrowed voice
   channel held by the modal" option the Task Prompt suggested, and it is
   behaviorally identical in production (a modal-submit interaction's
   `.channel` is the same channel it was opened from). One test
   (`test_modal_submit_records_intention_and_posts_timer`) asserted on
   `inter.channel.send` with `inter.channel` as a *separate* unrelated mock
   from the voice channel passed to the modal — updated the test to set
   `inter.channel = fake_voice_channel` so the fake matches how Discord
   actually wires modal-submit interactions.
7. `duration_minutes=session.duration_minutes,  # type: ignore[arg-type]`
   became an explicit `if duration_minutes is None: logger.error(...); return`
   guard inside the `_run_and_followup` closure — this is the one new,
   previously-untested branch; I did not add a dedicated test for it (see
   Issues) because triggering it requires the registry to report
   `duration_minutes=None` after `mark_active`, which the current
   `SessionRegistry` API makes awkward to construct without either
   reaching into private state or adding new registry surface — judged
   out of this Task's scope, and the guard is a straightforward one-line
   defensive check.
8. `bot=cast("TeaModeBot", self)` in `ViewsMixin._handle_timer_pick`:
   resolved with a structural `typing.Protocol` (`_ModalBot` in
   `views.py`) describing exactly the members `IntentionModal` reads from
   `bot` (`_registry`, `_voice_clients`, `_edit_states`,
   `_countdown_tasks`, `_on_countdown_tick`, `_run_end_of_session`).
   `IntentionModal.__init__`'s `bot` parameter is now typed `_ModalBot`
   instead of the concrete `TeaModeBot`, and `ViewsMixin` declares the
   same members (the two extra dict attributes as plain annotations, the
   two methods as `if TYPE_CHECKING:`-guarded stub declarations so they
   never shadow `TimerMixin`/`LifecycleMixin`'s real implementations at
   runtime via MRO). `self` then structurally satisfies `_ModalBot`
   without a cast or a self-type override. I first tried annotating
   `_handle_timer_pick(self: TeaModeBot, ...)` directly (the Task Prompt's
   other suggested option) but pyright rejects it
   (`reportGeneralTypeIssues`: "Type of parameter self must be a supertype
   of its class ViewsMixin") since `TeaModeBot` is not a supertype of
   `ViewsMixin` — the Protocol route is what actually type-checks.
9. `custom_id: str = interaction.data.get("custom_id", "")  # type: ignore[union-attr]`
   in `client.py` became an explicit narrow: `data = interaction.data`,
   return if `None`; `raw_custom_id = data.get("custom_id")`, return if not
   `isinstance(raw_custom_id, str)`.
10. `app/voice.py`'s `connect()`: `voice_channel.connect()` →
    `voice_channel.connect(cls=discord.VoiceClient)`, with an
    `isinstance(vc, discord.VoiceClient)` guard that logs a warning and
    raises `TypeError` on the (contractually impossible) else branch — per
    the Task Prompt's fallback instruction. This tightened
    `test_connect_calls_channel_connect_once` in `tests/test_voice.py`,
    which returned a bare unspec'd `MagicMock()` from the fake `connect`;
    updated it to `MagicMock(spec=discord.VoiceClient)`.
11. `app/db.py`'s `cur.lastrowid  # type: ignore[return-value]` became an
    explicit `if cur.lastrowid is None: raise RuntimeError(...)` guard —
    an INSERT that yields no rowid is a real failure, per the Task Prompt.
12. `interaction.user.voice if isinstance(interaction.user, discord.Member)
    else None  # type: ignore[union-attr]` in `commands.py` turned out not
    to need a `type: ignore` at all once the interaction's `.user` was
    bound to a local variable first (`user = interaction.user`) — pyright
    narrows the local variable through the ternary's `isinstance` check
    without help. No behavior change.
13. Ran the full validation pipeline after each cluster of changes; final
    run is clean (see Validation).

## Important Findings
- Confirmed a real, reusable pattern for this codebase's mixin-composition
  problem (`TeaModeBot(CommandsMixin, ViewsMixin, TimerMixin,
  LifecycleMixin)`): when a mixin method needs to pass `self` somewhere
  typed as the full composed class, a structural `Protocol` describing
  only the needed members — combined with `if TYPE_CHECKING:`-guarded
  method stubs on the mixin for members it doesn't own — avoids both
  `cast()` and the invalid "self must be a supertype" self-type override.
  Worth keeping as the standard approach if this pattern recurs in later
  Stages.
- The project's own Test Patterns convention (spec'd mocks for
  `isinstance` narrowing) was not yet applied to several existing
  `AsyncMock()`/`MagicMock()` fakes for `discord.TextChannel` in
  `test_session_handoff.py` and `test_bot_followup.py` — this Task
  brought the ones it touched in line, but there may be other unspec'd
  channel/member fakes elsewhere in the suite that would fail an
  `isinstance` narrowing if one were added there later.
