# Task 2.2 - Rate Limiting and Shared Session Start

## Summary
Added `app/rate_limit.py` (pure, clock-injectable per-user sliding window
and per-guild daily cap), extracted the `/teamode` handler body into a
shared `_start_session(self, interaction: discord.Interaction) -> None`
in `app/discord_bot/commands.py`, and enforced both limits there before
`create_pending_session`.

## Details
- **`app/rate_limit.py`**: `RateLimiter` class, constructed with a
  timezone (`tz: tzinfo`) plus injectable `monotonic` and `now` clocks.
  `check_and_record(user_id, guild_id) -> RateLimitResult` is the single
  entry point.
  - **Check-order decision** (documented in the class docstring and in
    the call site comment in `commands.py`): the per-user sliding window
    is checked first; a user refusal returns immediately without
    touching the guild counter. Only a call that clears *both* checks is
    recorded against *both* counters — so a refusal at either stage
    never partially records.
  - Per-user: `deque` of `monotonic()` timestamps per user; a call ages
    the deque's head out once `now - oldest >= RATE_LIMIT_WINDOW_SECONDS`,
    so the window slides continuously rather than resetting in blocks.
    Refusal's `retry_after_seconds` is `ceil(window - (now - oldest))`,
    floored at 1.
  - Per-guild: `(local_date_isoformat, count)` per guild, compared
    against `datetime.now(tz).astimezone(tz).date()` from the injected
    `now` clock — so the boundary is local midnight in the configured
    timezone, not UTC or wall-clock steps. A stored date that no longer
    matches today's date is treated as a fresh count of 0 (lazy
    rollover, no background timer needed).
- **Shared start function**: `_start_session` in
  `app/discord_bot/commands.py` is the full former body of
  `_handle_teamode` (guards 1–3, now the rate check, then session
  creation and welcome/participant-prompt posting). `_handle_teamode`
  is now a one-line delegator: `await self._start_session(interaction)`.
  Both are still on `CommandsMixin`, so a future component-interaction
  handler (e.g. a "Go again" button) can call `self._start_session(interaction)`
  directly with a button `discord.Interaction`.
- **Limit placement decision**: the rate check runs *after* guards 1–3
  (wrong channel / not in voice / active session) and *before*
  `create_pending_session` — so a mistyped channel or a user not in
  voice never burns the allowance, matching the Task Prompt's documented
  decision. Comment in `commands.py` states this explicitly.
- Refusal embeds reuse `COLORS["refusal"]` (muted grey) and plain
  `description` text (no `### ` prefix), matching the existing guard
  refusals exactly. `MSG_RATE_LIMIT_USER.format(seconds=...)` and
  `MSG_RATE_LIMIT_GUILD.format(cap=GUILD_DAILY_CAP)` are used verbatim
  from `app/constants.py`. Each refusal is logged at INFO
  (`logger.info`) with the user_id/guild_id and, for the user case, the
  retry-after seconds.
- **Bot wiring**: `TeaModeBot.__init__` (in `app/discord_bot/client.py`)
  now constructs `self._rate_limiter = RateLimiter(tz=TEAMODE_TIMEZONE)`
  (imported from `app.config`, which Task 2.1 added). `CommandsMixin`
  declares `_rate_limiter: RateLimiter` as a type-only attribute
  alongside the existing `_registry` declaration, following the
  established mixin pattern.
