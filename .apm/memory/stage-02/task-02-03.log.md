# Task 2.3 - Pending Expiry, Timer Robustness, Stale Buttons

## Summary

Added a pending-expiry watchdog, a shared `_on_session_terminal` cleanup
helper, a `spawn_logged` background-task wrapper, real 429-backoff gating,
and a unified stale-button refusal. Full validation pipeline is clean;
163 tests pass (156 pre-existing + 7 new).

## Details

- **`app/discord_bot/tasks.py`** (new) — `spawn_logged(coro, *, name) ->
  asyncio.Task[None]`: wraps *coro* in a small runner that catches and
  `logger.exception`s any exception other than `asyncio.CancelledError`
  (re-raised untouched). Every non-awaited `asyncio.create_task` call in
  the Discord layer now goes through this instead of calling
  `asyncio.create_task` directly:
  - `views.py` `IntentionModal.on_submit`'s post-countdown `_run_and_followup`
  - `lifecycle.py`'s follow-up watchdog and solo-grace arm
  - `lifecycle.py`'s new pending-expiry arm
  Tests that used to patch `app.discord_bot.<module>.asyncio.create_task`
  now patch `app.discord_bot.tasks.asyncio.create_task` (single shared
  location) — patch-path updates only, no assertion changes. Tests that
  captured the coroutine via a `side_effect` callback needed `**kwargs`
  added to their signature, since `spawn_logged` always passes `name=`.

- **Terminal helper** — `LifecycleMixin._on_session_terminal(self,
  session_id: int) -> None` (in `lifecycle.py`). Pops and cancels
  `_pending_expiry_tasks`, `_watchdog_tasks`, `_solo_grace_tasks`,
  `_countdown_tasks` (skipping cancel if the entry is the currently
  running task — avoids a pointless self-cancel when a task calls this
  from inside itself, e.g. the follow-up watchdog), and pops
  `_edit_states` / `_voice_clients`. Idempotent — safe to call after a
  call site already did some of this cleanup itself. Wired in at every
  terminal transition: `on_raw_reaction_add` (✅ and ⛔ → `completed`),
  the follow-up watchdog (`followup_timeout`), `_run_solo_grace`
  (`cancelled`), and `IntentionModal.on_submit`'s voice-connect-failure
  branch (`cancelled`). **Task 2.4 extends this same helper** with
  setup-message deletion and voice-channel status — no new call sites
  needed there.

- **Pending expiry** — `LifecycleMixin._arm_pending_expiry(session_id)`
  spawns `_run_pending_expiry(session_id, sleep_seconds=PENDING_TIMEOUT_SECONDS)`
  via `spawn_logged` and stores the task in `TeaModeBot._pending_expiry_tasks`
  (new dict, declared in `client.py`). `_start_session` (`commands.py`)
  calls it right after capturing the welcome message id. On timeout, if
  the session is still `PENDING`, `_run_pending_expiry` calls
  `mark_cancelled`, edits the welcome message via
  `channel.get_partial_message(id).edit(content=MSG_PENDING_EXPIRED,
  embed=<rebuilt welcome embed>, view=<all-disabled timer view>)`, and
  calls `_on_session_terminal`. `discord.NotFound` / `Forbidden` /
  `HTTPException` on that edit is caught and logged at WARNING.
  `ViewsMixin._handle_timer_pick` cancels and pops the expiry task
  right after `set_duration` — **note**: per the Task Prompt's explicit
  cancellation instruction, this means a session whose duration was
  picked but whose modal is then dismissed (never reaches
  `set_intention`) will no longer expire via this watchdog, even though
  it remains state `PENDING`. Flagged as `important_findings` since the
  Task Prompt's prose ("duration never picked, or modal dismissed")
  and its concrete cancellation instruction don't fully agree — I
  followed the concrete instruction and the given test criteria
  ("cancelled when a duration is picked"), but a future session stuck
  after a dismissed post-duration modal will not self-clean.
  `discord.ui.View` / embed builders were extended to support this:
  `_build_timer_view(session_id, *, disabled: bool = False)` builds an
  all-disabled row when `disabled=True`.

- **429 backoff gating** (`app/discord_bot/timer.py`) —
  `_EditState` (in `views.py`) gained
  `last_429_seconds_remaining: int | None = None`. On a 429, it's set to
  the tick's `seconds_remaining`, alongside the existing floor doubling.
  Before attempting an edit, `_on_countdown_tick` now checks
  `last_429_seconds_remaining is not None and (last_429_seconds_remaining
  - seconds_remaining) < backoff_floor` and returns early if so — no new
  clock, since `seconds_remaining` counts down ~1/real-second (per
  `run_countdown`'s drift correction). A successful edit resets both the
  floor and the gate. The final tick (0) is not special-cased, so it can
  still be skipped while inside the floor, per the Task Prompt.
  `edit_state.lock.locked()` check is confirmed dead code in production
  (`run_countdown` awaits `on_tick` inline) — left in place as a
  documented defensive no-op rather than removed, per the Task Prompt's
  "leave or remove it" choice.

- **Unified stale-button refusal** (`views.py`) — new
  `_session_actionable(session, *, expect: SessionState) -> bool` and
  `async _send_refusal(interaction, message) -> None` helpers.
  `_handle_timer_pick` now refuses (via `_send_refusal(...,
  MSG_SESSION_INACTIVE)`) when the session is missing **or not in the
  exact state the button expects** (`SessionState.PENDING` for a timer
  pick) — previously a duration-pick on an already-advanced session
  wasn't explicitly guarded. The non-facilitator refusal
  (`MSG_NOT_FACILITATOR`) is unchanged and still checked only after the
  session-actionable guard passes. `_send_refusal` is the single place
  future buttons should call for this styling/behavior.

- **Welcome-message capture** — `_start_session` (`commands.py`) now
  calls `await interaction.original_response()` right after
  `send_message` and stores `(channel_id, welcome_message_id)` in a new
  `_SetupMessages` dataclass (`views.py`), keyed by session_id in
  `TeaModeBot._setup_messages` (new dict). `_SetupMessages` also carries
  an `intention_message_id: int | None = None` field, unused by this
  Task but present for Task 2.4 to fill in without a schema change.

## Important Findings

The pending-expiry watchdog is cancelled as soon as a duration is
picked (per the Task Prompt's explicit instruction and its own test
criteria), not when the session actually advances past `PENDING`
(`set_intention`). A session where the facilitator picks a duration and
then dismisses the intention modal without submitting stays `PENDING`
forever with no expiry watchdog protecting it — it will sit inert until
a `/teamode-clear` or manual intervention. This is a real (if narrow)
gap; flagging for a decision on whether a later Task should re-arm
expiry on modal-dismiss, or accept the gap as-is.
