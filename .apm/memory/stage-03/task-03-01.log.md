# Task 3.1 - Embed Timer, Wrap-Up Phase and Nudge

## Summary
Replaced the plain-text active-timer message with an embed (Intention /
Facilitator / Started at fields, phase, countdown, progress bar) plus a
short content fallback, added the Deep focus → Wrap up switch and a
one-time wrap-up nudge, and froze the solo-grace final state's embed in
muted red. Full validation pipeline passes clean. Returning Partial only
for the required User Discord smoke test (step 10 of the Task Prompt).

## Details

### Builder and state
- New pure module `app/timer_format.py`: `format_mmss`,
  `format_progress_bar`, `select_phase`, `format_hhmm`, `should_nudge`.
  No `discord` or `app.config` import — `format_hhmm` takes `tz` as a
  parameter. 18 unit tests in `tests/test_timer_format.py`.
- The single content+embed builder is now
  `app.discord_bot.views._build_timer_message(*, intention,
  duration_minutes, facilitator_id, started_at, seconds_remaining,
  mention_line) -> tuple[str, discord.Embed]`. It replaces
  `_build_active_timer_content` (removed), which both the initial send
  (`IntentionModal.on_submit`) and every tick edit
  (`TimerMixin._on_countdown_tick`) call, so they can't drift apart.
- `_EditState` (app/discord_bot/views.py) gained two fields:
  - `started_at: datetime` — captured once via `views._now()` (a UTC
    `datetime.now(timezone.utc)`, patchable at `app.discord_bot.views._now`)
    in `on_submit`, right next to `mark_active`, and reused by every tick
    edit so "Started at" never drifts. The voice-status work mentioned in
    the Task Prompt should read `edit_state.started_at` for the same
    timing, rather than re-deriving it.
  - `nudge_sent: bool` — set the first time the wrap-up nudge fires for a
    session, so a later tick landing on the same trigger second (e.g.
    after a 429-backoff skip) never double-sends it. Lives on the same
    per-session dict (`bot._edit_states`), already torn down on every
    terminal transition via `_on_session_terminal`.
- `COLORS["wrap_up"]` added (built from `COLOR_OOLONG_AMBER`, same hex as
  `COLORS["completed"]`).
- `_format_intention_line`, `ACTIVE_TIMER_FMT`, and `INTENTION_LINE_SET`
  removed as unused (the Intention field now shows the raw intention text
  directly, since the field label "Intention" already supplies the
  context the old inline prefix provided).
- New constant `TIMER_FIELD_VALUE_MAX_LENGTH = 1024` (Discord's embed
  field-value hard limit) added to `app/constants.py`; the Intention
  field truncates to `TIMER_FIELD_VALUE_MAX_LENGTH - 1` chars + `…` when
  over (intentions can be up to `INTENTION_MAX_LENGTH` = 4000 chars).

### Embed layout and the `### ` rule
- Fields (all `inline=False` — mobile clips to ~340px, forcing single
  column anyway): Intention, Facilitator (`<@{current facilitator}>` —
  `session.handoff_facilitator_id or session.facilitator_id`, so a
  handoff shows on the *next* tick edit after `mark_handoff`), Started at
  (`format_hhmm(started_at, TEAMODE_TIMEZONE)`).
- Description: three lines, each prefixed `### ` per UI-ADR — phase,
  `TIMER_REMAINING`, then the progress-bar line — in that order, matching
  `FocusTimerWidget`'s layout intent (fields conceptually "before" the
  phase/countdown/progress group). Note: Discord actually renders an
  embed's fields *below* its description, not above — so the on-wire
  visual order is description (phase/countdown/progress) then fields
  (Intention/Facilitator/Started at). Per the Task Prompt's own guidance
  ("keep it simple rather than fighting Discord's layout"), I did not try
  to force fields-first; flagging this for `UI-ADR.md` when it's updated.
- Accent: `COLORS["active"]` (matcha sage) in Deep focus,
  `COLORS["wrap_up"]` (oolong amber) in Wrap up.
- Content fallback: `TIMER_CONTENT.format(mmss=...)` + `\n` + the stored
  mention line when non-empty — unchanged mechanism from before, just
  shorter now that the full state lives in the embed.

### Nudge and solo-grace
- `TimerMixin._on_countdown_tick` checks `should_nudge` before the
  `% EDIT_INTERVAL_SECONDS` early return (so the trigger doesn't have to
  land on an edit-cadence boundary, even though it does today at
  `WRAP_UP_MINUTES * 60 = 180s`), re-verifies the session is still
  `SessionState.ACTIVE` at fire time, sets `nudge_sent`, and sends
  `MSG_WRAP_UP_NUDGE` on the timer message's channel
  (`edit_state.message.channel`). Send failures are caught
  (`discord.HTTPException`) and logged at WARNING; they never affect
  `nudge_sent` (already set) or the tick's edit path.
- Solo-grace final state (`LifecycleMixin._run_solo_grace`, lifecycle.py):
  copies the last embed (`edit_state.message.embeds[0].copy()`), recolors
  it `COLORS["crashed"]` (muted red), and edits with
  `content=SOLO_GRACE_ENDED, embed=frozen_embed`. No further edits follow
  — the edit state is already popped earlier in the same function.

## Important Findings

**`NUDGE_MIN_DURATION_MINUTES` changed on disk during this Task, from 20
(as stated in the Task Prompt's dependency-context summary) to 10** — I
did not make this change; the harness flagged it as a concurrent
modification partway through implementation. This shifts which of the
built-in duration buttons (`DURATIONS_MINUTES = (5, 10, 25, 50)`) get a
wrap-up nudge: previously only 25/50-min sessions did (matching the Task
Prompt's explicit "never for 5/10-min sessions" wording); now a 10-min
session also nudges once (7 min Deep focus, nudge at the 3-min Wrap-up
boundary), and only the 5-min session never nudges. I followed
"Instruction Accuracy" (trust the code over the prompt on contradiction)
and built/tested against the live value (10): my automated bot-level
"never nudges" test uses a 5-min session (true under either 10 or 20),
and the pure `should_nudge` unit tests are written against the imported
constants rather than a hardcoded threshold, so they hold regardless.
Flagging this because:
1. It's a behavior change nobody asked for in this Task's scope — worth
   confirming intentional before merge.
2. The smoke-test checklist below now expects a 10-min session to also
   nudge, not just 25/50-min — different from the Task Prompt's literal
   wording.

No other unexpected findings. No compatibility issues — the change is
additive to the message shape (content still present, now shorter) and
every existing caller of the removed `_build_active_timer_content` /
`ACTIVE_TIMER_FMT` was updated in the same commit.
