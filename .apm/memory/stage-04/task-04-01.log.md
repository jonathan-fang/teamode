# Task 4.1 - Go Again and Break

## Summary
Implemented the post-follow-up chaining prompt (Go again / break offer),
the Go again hand-off, and the five-minute break lifecycle (start,
cancellation by a new session, completion with reverie and a post-break
Go again button, and its own expiry). All automated validation passes;
the User's manual Discord smoke test (step 8 of the Task Prompt) is
outstanding.

## Details
New module `app/discord_bot/breaks.py` holds `BreakMixin` (mixed into
`TeaModeBot` alongside the existing mixins) plus two dataclasses:

- `_ChainState(session_id, channel_id, message_id, kind, timeout_task)`
  — the standing chaining prompt in one text channel. `kind` is
  `"chain"` (Go again + break, posted after ✅/⛔) or `"post_break"`
  (Go again only, posted after a break ends). `timeout_task` is set
  only for `"post_break"`.
- `_BreakState(task, message_id, end_time, session_id)` — an
  in-progress break in one text channel. `session_id` is the session
  whose chaining prompt started the break, reused in the post-break
  Go again button's custom_id.

Both are keyed by text-channel id in two new `TeaModeBot.__init__`
dicts: `self._chain_states` and `self._break_states` (in-memory only,
lost on restart, per the existing pattern for `_channel_cleanup` etc.).

**Chaining prompt** — `LifecycleMixin.on_raw_reaction_add` now calls
`BreakMixin._post_chain_prompt(session_id, text_channel_id)` after a
facilitator ✅ (right after `_on_session_terminal`) and after a
facilitator ⛔ (after the "why" line send, whether it succeeds or the
channel isn't sendable). It is never called from the follow-up
watchdog, so a follow-up timeout never gets one. `_post_chain_prompt`
sends `CHAIN_PROMPT` with a two-button view
(`teamode:<session_id>:again`, `teamode:<session_id>:break`) and stores
the resulting `_ChainState`; a send failure is logged at WARNING and
leaves no state behind.

**Chain validity rule** — `client.py`'s `on_interaction` router adds
`purpose == "again"` → `_handle_go_again` and `purpose == "break"` →
`_handle_break`. Both look up `self._chain_states[interaction.channel_id]`
and refuse with `MSG_SESSION_INACTIVE` unless it exists and its
`session_id` matches the button's — this replaces the generic
stale-session refusal for these two purposes only, per the Task Prompt.
`_clear_chain_state(channel_id)` pops the state, cancels its
`timeout_task` if any, and disables its message's buttons via a channel
edit (WARNING on failure) — called on break start and, from
`CommandsMixin._start_session`, on every new session start (`/teamode`
or Go again). The post-break Go again timeout (`_run_go_again_timeout`)
pops and disables directly rather than calling `_clear_chain_state`, to
avoid a task cancelling itself mid-edit.

**Go again** — `_handle_go_again` checks chain validity then calls
`self._start_session(interaction)` unchanged; the clicker becomes
facilitator through the exact same guards, rate limit, and welcome flow
as `/teamode`. No changes to `_start_session`'s guard logic were
needed — it already accepted a generic `discord.Interaction`.

**Break** — `_handle_break` additionally requires the clicker be in the
voice channel (`MSG_NOT_IN_VOICE` otherwise, chain state untouched).
On a valid click: clears the chain state, `interaction.response.defer()`,
sends `BREAK_STARTED.format(hhmm=...)` (now + `BREAK_MINUTES`, via
`timer_format.format_hhmm` and `TEAMODE_TIMEZONE`), and spawns
`_run_break` via `spawn_logged`. No DB row, no voice status. `_run_break`
sleeps `BREAK_MINUTES * 60`, then (if not cancelled) connects voice,
plays the reverie (`voice.play_reverie_then_disconnect`, which also
disconnects), posts `BREAK_OVER` with a single Go again button reusing
the original `session_id`, records a new `"post_break"` `_ChainState`,
and spawns `_run_go_again_timeout` (`GO_AGAIN_TIMEOUT_SECONDS`, disables
the button on expiry). A voice-connect failure is logged at WARNING and
`BREAK_OVER` is still posted, per spec.

**Break cancellation** — `CommandsMixin._start_session` calls
`self._clear_chain_state(interaction.channel.id)` then
`self._cancel_break(interaction.channel.id)` right after session
creation, alongside the existing previous-session cleanup.
`_cancel_break` cancels the break task and edits the break message to
`BREAK_CANCELLED` (WARNING on failure).

Both mixins declare the other's methods/attributes as `TYPE_CHECKING`
stubs (matching the existing `_arm_pending_expiry` pattern), so pyright
type-checks each mixin in isolation with no `cast()` / `# type: ignore`.

Updated `tests/test_bot_followup.py`'s
`test_facilitator_no_entry_marks_completed_0_and_posts_why`: the ⛔
path now sends two messages (why line, then chain prompt) on the same
fake channel, so the assertion changed from `assert_awaited_once` to
checking both calls in order.
